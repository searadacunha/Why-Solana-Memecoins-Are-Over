The new calculation is the one every feature now uses (fparse.leg_sol). The detector's tickets come from the program's TradeEvents; the System transfers to the curve reproduce them.

Second correction (2026-09-29): the creation transaction. The curve's token balance rises there (the supply lands on it), so the first parser never read it as a buy, and the creator's own first buy was missing from the tickets; when it is 5 SOL or more the detector counts it as a ticket. It is now read from the creator's System transfer to the curve (fparse.curve_transfers, without the rent that creates the curve account), and counted in the bundle tickets when it reaches 5 SOL; the creator keeps its own role for the wallet features. `b_creator_buy_sol` read a field the parser never wrote and was 0 everywhere; it now reads the same transfer.

Version-1 transactions (on mainnet from mid-September 2026). The detector fetches the creation slot with maxSupportedTransactionVersion 0 and silently drops the version-1 transactions, so a sniper who bought only through one is missing from its tickets. The collectors of this study ask for version 1, so the bundle features count that sniper: they describe the chain, not the detector's view of it. The alert population itself is what the detector raised, with that blind spot.
